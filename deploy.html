Deployment

Deployment

WorkSigned runs on the institution's network, under the institution's control, and attaches to the storage and compute it already operates. Only one component is outside that network — the signing authority — which is operated by WorkSigned or an approved institution, never by the platform operator. The proof model is the same in every configuration (see Proof). This page is for the teams responsible for integration, security, and procurement: what runs where, what each side owns and configures, and the security and compliance posture.

How it runs

Two choices define the deployment. The client — the native desktop app (with local-file access) or the browser (no local-file access, but the same tools and office suite, reachable from any device on the network). And where auth and user data live — in the institution's cloud, or entirely on the institution's own machines. Research data is a separate matter: it always stays on the institution's backends and is attached, not moved.

Desktop + institutional cloud
Recommended
Desktop app with local files and the office suite; online sign-in through the institution's identity provider; user data in the institution's cloud.
Browser + institutional cloud
Recommended
The same, in the browser. The only difference: no access to local files. Reachable from any device on the network.
Desktop + fully on-prem
Maximum privacy
Sign-in is on the institution's own machines and user data stays local. The most restrictive option — confirm it fits the identity and access policy before choosing it.

The components that hold the data are never the same components that hold the signing key. That separation is what lets a record be verified without trusting the data store.

WorkSigned does not require storage to be standardized or migrated. If the institution runs a mix of S3, NFS, an HPC cluster, and a repository — as most do — each is attached with its native protocol and each is recorded the same way.

Data & its access

WorkSigned attaches to the storage and compute the institution already runs. In the workspace they appear as ordinary folders; the data does not move, jobs keep reading and writing the same paths, and access levels follow the permissions the backend already enforces — the platform never grants more access than the backend has been granted. Every non-local connection uses the backend’s own authentication (S3 keys, SSH/SFTP keys, NFS Kerberos, a service account, a repository token).

How that is secured:

  • Credentials are encrypted and stored on the institution's side — they are never sent back to a browser once configured.
  • The decryption key is held by the institution, so the institution can audit and decrypt — or, as an option, by the individual user alone, so that even WorkSigned cannot read the credential.
  • Every use of a credential is logged — which connection, which user, when, and the result. Deleting a connection deletes its credential.
  • For HPC: jobs keep running natively on Slurm; WorkSigned watches the output directories and records the results — optionally per-job, automatically.

The full list of supported backends and the integration options (read-only, read-write, deposit; the HPC modes) are in technical detail.

Who signs, and who holds the key

The trust anchor is the signing authority. It holds a private key that never leaves it, signs only the fingerprints (hashes) of the WorkSigned Record — never the underlying files — and runs on an immutable, hash-verified image. Because it only ever sees hashes, it does not need to trust the data, and verifiers do not need to trust its storage. Verifying a seal requires only its public key and the WorkSigned Record.

Signatures come from the WorkSigned signing network — WorkSigned plus a small number of approved institutions, each signing with its own key. A deploying institution is not automatically a signer: it controls the platform, the sign-in, and its own data, and may opt in to joining the network as an approved authority in its own right (a distinct role with its own key custody). The full model, including multi-authority co-signing, is on the Proof page.

Security & compliance posture

  • Single sign-on. Users sign in with their existing credentials via the institution's identity provider (SAML 2.0 or OpenID Connect; CAS supported) — no second account.
  • No public endpoint required. On-prem, researchers reach the platform over the institution's intranet or VPN. The signing authority is never a public endpoint and never exposes the private key.
  • Least-privilege, per user. Each user operates only the connections they are authorized for; each connection’s access level is enforced by the backend, not just the interface.
  • Authenticated internal services. The platform’s services verify each other with cryptographic tokens; a component that cannot present a valid token is refused.
  • Credentials never stored in plaintext. Encrypted in a credential store, institution- or user-keyed.
  • No training on institutional data. AI work runs on models that do not train on institutional content, or on the institution's own endpoint, where the model is controlled in-house.
  • Data stays in the institution's jurisdiction. Research data, the WorkSigned Record, and (in on-prem modes) the signing key remain on systems the institution controls. There is no requirement to upload to a vendor cloud.
  • Independent verification. Any third party — a committee, a funder, a journal — can verify a sealed record against the signing authority’s public key and the WorkSigned Record, without involving the institution or the data store.

AI (LLM) backends

AI-assisted work runs on the institution's hosted LLMs by default, or on WorkSigned’s private LLMs, or on a private endpoint the institution controls — in every case on models that do not train on institutional data. The platform speaks the standard OpenAI-compatible chat-completions API, so any endpoint that implements it works. In on-prem mode, no prompt or completion ever leaves the institution's hardware.

The AI conversation itself is captured on the WorkSigned Record, so AI-assisted work is attributable just like any human contribution.

Access modes. A connection can be read-only (browse, open, download), read-write (plus save edits), or read + deposit (deposit as a new version, for repositories). A project can have several at once, and each is recorded independently.

HPC / Slurm / Lustre

On a research cluster the storage (Lustre, GPFS, NFS) is already mounted by the kernel and the jobs already read and write those paths natively on Slurm. WorkSigned does not replace any of that. Three integration depths:

  • Watch outputs only (recommended default). Jobs run natively with zero platform involvement in the compute loop. The platform watches configured output directories, hashes the results, and appends them to the WorkSigned Record.
  • Add browser editing. The platform also proxies file reads and writes for the browser editor, so a researcher can view a result, edit a config, or check a log without SSH’ing in. Writes go directly to the cluster filesystem.
  • Import. Where a direct connection is not available, a one-time or scheduled transfer brings a snapshot of the outputs into an attached backend, and the record works on the copy.
Per-job records. An optional cluster-side setting (a Slurm epilog hook) can automatically hash every job’s output directory and record it with the job metadata — so every job is recorded without the researcher doing anything.

Network

  • Users → platform. Over the institution's intranet or VPN. No public internet endpoint is required for an on-prem deployment.
  • Platform → backends. Ordinary internal connections from the job services to each backend they attach to, each using the backend’s native transport. For storage that does not send the browser headers the client needs (typical of on-prem object stores and NFS), requests are routed through a server-side proxy on your network — the browser never talks directly to raw storage.
  • Signing authority. Reached only by the components that request signatures. Never publicly exposed.
