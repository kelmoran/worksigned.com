Trust & Verification

How the proof works

A WorkSigned Record is a record of your work that anyone can check for themselves — with only a public key, the record, and the timestamps — without relying on our servers or our word.

The one idea. We do not read or upload your files. We sign a 32-byte fingerprint of your WorkSigned Record. Because the fingerprint changes completely when even one byte changes, “the authority signed fingerprint H” is the same as “the authority signed this exact record.”

How it works, end to end

Here is the whole thing, in order. Each step shows what happens and a concrete example of what that piece looks like. The only technical word used is hash — a fixed-length fingerprint of a file that changes completely when even one byte of the file changes.

1
You work
You edit and save files in your project, the normal way.
2
The platform records
It captures what you do, down to the keystroke — edits, saves, terminal commands, search queries, and chat messages. Your files and logs are never sent to us.
3
A record forms
Those events build your WorkSigned Record — a running, time-stamped list of your work, fine-grained, not just a snapshot.
# Step 1-3 · your activity, as the platform records it (fine-grained) Wed 09:14:02 methods.tex key typed \frac{a}{b} Wed 09:14:09 methods.tex key backspace, typed \frac{a+1}{b} Wed 09:14:41 methods.tex save file saved Wed 11:02:33 terminal cmd python analysis.py Wed 13:20:10 search query \"tamper-evident logging\" Wed 15:40:55 chat msg \"baseline confirmed\" Thu 08:22:19 results.csv save file saved → every event, in order, is your WorkSigned Record — not a single snapshot
4
One hash of everything
On each seal (daily, or when you choose), we hash every file in the project and fold all those hashes into a single hash.
5
Only the hash travels
This is the only thing that leaves your servers: one hash. No files, no record, no logs — nothing readable about your work.
6
An independent clock
A trusted third party (a TSA) stamps the time the hash was seen.
# Step 4 · one hash that covers the whole project hash( methods.tex ) = 9f2c...a1 hash( fig1.pdf ) = 4d7e...b8 hash( analysis.ipynb ) = c3aa...02 hash( results.csv ) = 7719...e4 fold all together → one hash of the whole project = 3b9f4a…77c2 change any byte in any file → this single hash changes completely
What actually leaves your servers. At sealing time, exactly one value is sent to the signing authority: the single hash above. Nothing else crosses the boundary — no file content, no file names, no keystrokes, no chat, no record. The hash is a fixed-length number with no way to read back from it. If a verifier or an auditor ever wants to know what left your machine, the answer is: one hash, and only that one hash.
7
It is signed
The authority writes the hash and the time together into one line, then signs that whole line with its private key. Because the time is inside the signed line, you cannot change the time (or the hash) without breaking the signature.
8
A signature comes back
You get the hash + the time + the signature + the authority’s public key. Together these are the seal.
9
You keep it
You (or your university) store the seal. It is yours; it does not live on our servers.
# Step 7 · how the time gets bound into the signature the line that is actually signed (hash + time written together): worksigned | gene-editing | user-42 | ts = 2026-09-22T00:00Z | hash = 3b9f4a…77c2 ↓ private key applied to that whole line → signature 487d…9c1e change the time OR the hash → the line changes → the signature breaks
# Step 8 · what the authority returns (the seal) hash 3b9f4a…77c2 what was signed time Wed 2026-09-22 00:00 bound into the signature; also TSA-stamped signature 487d…9c1e made by the authority’s private key public key -----BEGIN PUBLIC KEY----- so anyone can check it
Step 10 · Verification & a dispute. In a dispute, you hand the seal (and your files) to a journal, funder, or court. On their own machine they re-hash your files and compare to the seal’s hash, check the signature against the included public key, and confirm the time stamp against the TSA. The result is decided by the checks — valid or not — and does not depend on us saying anything.

Hash-commitment signing

Every save and edit adds an entry to your project’s record: the file, its content hash (SHA-256), and a time. Each entry links to the one before it. A signature is made over a fingerprint of that record — a hash that changes completely when even one byte changes. So a signature over the fingerprint is a signature over the entire record. The authority does not need the files.

The three guarantees

Sole signer
One private key
The private key lives only on the signing authority. No one else can make a valid signature with it — not you, not an administrator, not us.
No file upload
Only hashes travel
Only fingerprints are sent to the authority. The signature is a small, fixed-size value, the same whether your project is one file or ten thousand.
Self-verifying
Anyone, offline
A third party checks the signature using only the public key (included in the sealed bundle) and the record. The check does not require WorkSigned's servers or databases.

Independent time anchoring

File times are local and can be changed. WorkSigned does not rely on them. It asks an independent RFC 3161 Time-Stamp Authority (TSA) to stamp the record; the TSA returns a signed token with its own clock, the value it stamped, and a serial number. The token can be checked later against the TSA’s public certificate, with no need to contact the TSA.

Each seal carries its own independent timestamp, so a steady clock offset shows up as a constant shift, not a growing one, and the first stamp fixes where the timeline begins. The times are anchored to an external clock, not one anyone in a dispute could adjust.

What the seal proves

At time T, the signing authority committed to a fingerprint H. Because H is a fingerprint of the entire record, that attestation means:

The record existed
Byte-for-byte
The full record — every file, every edit, every entry — was exactly what it is now, at time T. Change one byte and the signature no longer holds.
The authority saw it
The fingerprint
The authority saw the hash of your exact record. “I signed H” is the same as “I saw this exact record.”
The time is real
TSA-stamped
The timestamp is signed by an independent TSA — an external clock, not the researcher’s machine.
Stated plainly. A seal proves you had this exact body of work — the files, the edits, the sequence — at time T. That is the claim that matters in a priority or intellectual-property question: it establishes who had the work first. It does not claim the work was original, or that the idea happened at that moment. The strength is in the process: a complete, time-anchored record of how the work developed, which is hard to fabricate.

Multi-authority

A record can be co-signed by multiple independent authorities, each with its own key. Each seal links to the previous one, so tampering at any point is detectable. Because each signer holds a key the researcher cannot access, no one on the machine — researcher, administrator, or operator — can forge a seal. If one signer fails, the others still stand.

Built on open standards

The record is not a proprietary format. It is assembled from a small set of open, published standards, each doing one job. A verifier does not have to trust WorkSigned: they check the work against the standard itself.

StandardWhat it doesWhy it matters
RFC 3161
IETF Time-Stamp Protocol		 A signed time-stamp token from an independent TSA — an external clock. An independently anchored time.
Merkle tree
Certificate-Transparency style (RFC 6962)		 Hashes every file and folds them into a single root; the authority signs that root. A commit to exactly which files existed at sealing. Recompute it and it matches — or it does not.
Hash chain
Tamper-evident audit record		 Each activity entry links to the hash of the one before it; the end of the chain is signed. The sequence is tamper-evident. Drop, reorder, or edit any entry and it no longer checks out.
Why several, not one. The time anchor (RFC 3161), the commit to the file tree (Merkle), and the sequence (hash chain) are independent of one another. If any single one became obsolete or its operator disappeared, the others still hold.
What it is not. WorkSigned does not verify a person’s identity, and does not produce archival documents. It verifies authorship of a file tree and time, in a form any third party can re-check.

The verification experience

Verification is something a journal, funder, or court does themselves, not something they ask us to do. Given the record and the sealed bundle (which includes the public key), a verifier:

1  Re-hashes the files and checks the Merkle root.
2  Verifies each signature against the included public key.
3  Checks the chain — each seal links to the one before it.
4  Confirms the timestamp against the TSA’s certificate.
5  Result: VALID.

No reliance on our infrastructure is needed at any step.

Auditable signing

The authority runs on an immutable, hash-verified image: the exact code that produced the seals is fixed at deploy time and its hash is published, so anyone can confirm what ran. Each signature is written to an append-only signing log, stored apart from the live signing service. The log holds only fingerprints and signatures — there is no field in it where your data could go. A read-only view exposes the log and the public keys; never the private key, never file contents.

The private key never leaves the authority — the same model as an HSM or TPM: the key stays on trusted hardware, the code is auditable, and the log is tamper-evident.

Lightweight by design

Because only fingerprints are stored, the authority’s footprint is small — a few hundred bytes per seal. The platform is selling trust and verification, not storage, and the architecture keeps that cost near zero.
