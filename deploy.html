Deployment

Deployment & architecture

WorkSigned runs on a small set of services with a clear separation between your data and the signing trust. The platform runs on your own network under your control, and it attaches to the storage and compute you already operate. The only component that is not on your network is the signing authority — which is always operated by WorkSigned or an approved institution, never by the platform operator. This page is written for the people who have to green-light it: it covers the deployment modes, the mounting system that lets WorkSigned attach to your existing storage and compute, and the practical requirements your infrastructure team needs. The proof model is the same in every configuration.

Same proof, any configuration. Whether you use the desktop client or the browser, and whether auth is online or local, the record is captured, hash-chained, and sealed the same way. What changes is the client and where auth and user data live — not how the proof is produced or verified.

The modes

The platform runs on your network in every configuration. Two independent choices define the configuration:

  • The client. The native desktop client gives the platform access to local files; the browser client has no local-file access but runs the same tools and office suite, and can be reached from any device on your network.
  • Where auth and user data live. In cloud configuration, authentication is online and user data (settings, sessions, the record) is stored in the cloud. In a non-cloud configuration, auth is local-machine based, the job server runs on your own machine, and user data stays local.

Combined, that gives three practical configurations. Research data is not one of these choices: it always lives on your own backends, mounted in (see mounting). See infrastructure footprint for what your team provisions.

Desktop + cloud

The native desktop client runs on the researcher’s machine with access to local files and the desktop office suite. Authentication is online through your identity provider, and user data — settings, sessions, and the WorkSigned Record — is stored in your cloud. Research data is not involved in this choice: it lives on your own backends and is mounted into projects. The platform servers run on your network; only the signing authority uses WorkSigned / approved cloud services.

Browser + cloud

The same configuration as desktop + cloud, but accessed in a web browser. The browser client has no access to local files — that is the only difference. It runs the same office suite and the same tools, and work happens in the browser and in your mounted backends. Because it is browser-based, it can be reached from any device on your network. Auth is through your identity provider and user data lives in your cloud; the platform runs on your network; only the signing authority uses WorkSigned / approved cloud.

Desktop + local (non-cloud)

In this configuration, authentication is local-machine based rather than online, the job server runs on your own machine, and user data (settings, sessions, the WorkSigned Record) stays local. Research data is still mounted from your own backends. This is a special configuration for maximum privacy — the trade-off is that it is more restrictive (no cross-machine sessions, a simpler auth model) and some IT policies do not allow it. The signing authority is still WorkSigned / approved cloud.

A fully local, offline operation is possible for the record on your own machine, but the signing authority remains external to the platform — it is never a component the deploying institution co-locates with its data. See signing authority.
The mounting system

How mounting works

WorkSigned mounts the storage and compute you already have, presents them as a single workspace in the browser, and adds the signed record on top — without relocating your data, replacing your compute, or changing how your researchers’ code reads and writes files.

A mount is the user-facing idea: a path in the WorkSigned file tree that shows you files (and, depending on the backend, lets you read, edit, or run on them) from a system that lives elsewhere. From the user’s point of view it is just a folder. Underneath, a capability-aware adapter implements the backend’s native protocol, so the same file-tree UI works whether the bytes are on an S3 bucket, an NFS share, a lab server over SFTP, or a 500-node HPC cluster — the user sees paths, never protocols.

In short: WorkSigned attaches to your existing compute and storage — HPC, cloud, lab server, institutional repository — and adds a tamper-evident, signed record on top. Your data does not move. Your compute does not change. The platform runs on your systems under your control, and the record is signed by the trusted signing network.

Supported backends

WorkSigned implements the native protocol of each backend rather than requiring a uniform file server. Each backend reports a set of capabilities — whether it supports reading, writing, executing commands, random access, versioning, and so on — and the platform’s UI degrades gracefully to exactly what that backend can do.

HPC / Slurm / Lustre

At research-intensive universities, the cluster’s storage (Lustre, GPFS, NFS) is already mounted by the kernel, and the researchers’ jobs already read and write those paths natively on Slurm. WorkSigned does not replace any of that.

Three integration depths are supported:

  • Observer (recommended default). The researchers’ jobs run natively on Slurm with zero WorkSigned involvement in the compute loop. The platform watches configured output directories, hashes the results, and appends them to the WorkSigned Record — the platform becomes the trust layer on top of the existing cluster.
  • Interactive. The platform also proxies file reads and writes for the browser editor, so a researcher can view a result PDF, edit a config, or check a log without SSH’ing into the cluster. Writes go directly to the cluster filesystem.
  • Import. Where a direct connection is not available, a one-time (or scheduled) transfer brings a snapshot of the outputs into a mounted backend, and the WorkSigned Record works on the copy.
Per-job WorkSigned Records. A Slurm epilog hook can automatically hash every job’s output directory and record it with the job metadata (job ID, user, wall time, nodes) — so every job on the cluster is recorded without the researcher doing anything. The compute stays native; only the trust layer is added.

Mount modes: read-only, read-write, deposit

Each mount is created within a project and, like a normal mount point, can be drilled into like a directory. The user does not see the mount mechanics after creation — just a path. The mode of a mount reflects what the underlying backend actually permits:

ModeCapabilitiesExamples
Read-onlyBrowse, open, view, download to workspaceExisting repository items, imported snapshots, a share you only have read access to.
Read-writeEverything read-only, plus save editsS3, NFS, SFTP, the HPC login node, local disk.
Read + depositRead and browse, plus “deposit as new version”Institutional repositories where “write” means a new versioned deposit, not in-place edit.

A project may have several mounts at once — for example a read-write S3 mount for working files plus a read-only repository mount for published reference material — and each is recorded and sealed independently.

Mount credentials & authentication

Every non-local mount requires authentication — a token, a key, or credentials against the backend’s own auth (S3 keys, SFTP/SSH keys, NFS Kerberos, Azure SAS, a service account, a repository token). The key design points for a security review:

  • Secrets are stored server-side, per user, and never returned to the browser after they are saved. The client never holds the underlying credentials in the clear once a mount is configured.
  • Encrypted at rest. Mount credentials are encrypted in the credential store using per-user envelope encryption — never stored in plaintext.
  • Your choice of key custody. By default the encryption key is institution-held, so your institution can decrypt and audit — which is what most institutions want for compliance. As an option, a user-wrapped key makes the secret zero-knowledge to both the institution and the vendor: they store only the encrypted blob and cannot read the credential.
  • Per-credential audit log. Every time a mount’s credential is used, an audit entry records which mount, which user, when, and the result.
  • Revocation. Deleting a mount deletes its credential; an administrator can wipe a user’s credential store; individual credentials can carry an expiry. Deleting the mount is the only thing that removes the credential — nothing lingers.

Backend auth is separate from WorkSigned platform auth: WorkSigned signs you in to the platform (see identity & access), and each mount separately authenticates to its own backend using that backend’s native method.

The signing authority

Across all modes, the trust anchor is the signing authority: it holds a private key that never leaves it, signs only fingerprints of your WorkSigned Record, and runs on an immutable, hash-verified image. It signs only hashes and never sees your files, so it does not need to trust your data, and you do not need to trust its storage. Verification of any seal requires only its public key and your WorkSigned Record.

Who operates the authority is separate from who deploys the platform. In every configuration, signatures come from the WorkSigned signing network — WorkSigned plus a small number of approved institutions that act as Trusted Research Signing Authorities, each signing the hashes with its own key. A deploying institution is not automatically a signer; it controls the platform, the auth, and its own data, and may opt in to joining the signing network as an approved authority in its own right (a distinct role with its own key-custody responsibility). See Proof & signing for the full model, including multi-authority co-signing.

For IT

What IT needs to provide

A WorkSigned deployment is a small, well-bounded set of services — not a monolith and not a new storage platform. On-prem, the team provisions a modest number of servers (typically in the low single digits) plus the backends they already operate, which are mounted rather than replaced. WorkSigned’s own footprint is deliberately small because the heavy data and compute already live on your existing systems.

What to provideWhy

Your existing storage / computeS3-compatible, NFS, SFTP, an HPC cluster, a repository — mounted, not migrated (see mounting).

WorkSigned does not require you to standardize or migrate storage. If you run a mix of S3 and NFS and an HPC cluster and a repository — as most institutions do — each is mounted with its native protocol and each is recorded the same way.

Infrastructure footprint

The deployment is deliberately split so that your research data, your user state, the proof/WorkSigned Record, and the signing trust can be hosted independently — which makes backup, load-balancing, and audit boundaries cleaner, and means a multi-tenant institution can run several job servers in front of the same data stores. Where each piece lives is a per-institution choice; the table below shows the responsibilities, not mandated instance sizes.

ResponsibilityTypically hosted onHolds
Frontend / gatewayYour networkNothing user-specific (stateless).
Job & trust server(s)Your servers (horizontally scalable)The WorkSigned Record and app state — no user content.
Research dataYour existing backends (mounted)Project files — stays where it is.
User stateYour serversSettings, sessions, mount list — separate from research data.
WorkSigned RecordYour servers (optionally on its own host)The append-only, hash-chained record; sealed and signed bundles.

Separating the user-data store, the sub-app runtimes, the webapp, and the third-party file servers is a deliberate design choice: it is easier to back up, easier to load-balance and route, and easier to debug when each has a single, clear job. Institutions that want maximum separation can host the WorkSigned Record, user-state, and auth on their own dedicated hosts, distinct from the rest. The signing authority is part of the external signing network (or an approved authority the institution joins) rather than a component the platform operator co-locates with its data.

Network & connectivity

  • Users → frontend. Researchers reach the platform over your intranet (or VPN). No public internet endpoint is required for an on-prem deployment.
  • Application servers → mounted backends. The job & trust server needs network reachability to each backend it mounts (your object store, NFS export, SFTP host, repository API, and the HPC login node). These are ordinary east-west connections on your network; each uses the backend’s native transport.
  • Backend proxy. For storage that does not send the browser headers the client requires (typical of on-prem object stores and NFS), requests are routed through a server-side proxy on your network — the browser never talks directly to raw storage.
  • HPC login node. Reached directly over your internal network, authenticated by a shared token. No public exposure.
  • Signing authority. Reached only by the components that request signatures; it is never a public endpoint and never exposes the private key.

Local / desktop mode needs none of the above beyond your machine (loopback). Cloud mode replaces the on-prem east-west connections with connections from WorkSigned’s infrastructure — or, where a project still mounts your own backends, the same backend connections described here.

Identity & access

Platform login is separate from backend auth and is designed to integrate with your existing identity infrastructure:

  • Institution SSO. WorkSigned integrates with your identity provider so users sign in with their existing credentials rather than a second account. The supported protocols are the standard enterprise ones — SAML 2.0 and OpenID Connect — with CAS as a supported integration path for institutions that run it.
  • Least-privilege, per-user. Each user sees and can operate only the mounts they are authorized for, and each mount’s capability (read / read-write / deposit / run) is enforced by the backend, not merely by the UI.
  • Service-to-service auth. Internal services authenticate each other with verified cryptographic tokens; a component that cannot present a valid token is refused.
  • Local mode. Where no IdP is involved, the user is their own authority — self-contained, no external account.
Backend authentication (S3 keys, SSH/SFTP keys, NFS Kerberos, a repository token, an HPC token) is separate and uses each backend’s native method — see mount credentials & authentication.

Data residency & compliance

  • Data stays in your jurisdiction. In on-prem and sovereign modes, research data, the WorkSigned Record, and the signing key all remain on systems under your control. There is no data-gravity requirement to upload to a vendor cloud.
  • No training on your data. AI-assisted work runs on dedicated models that do not train on your content, or on your own on-prem endpoint where you control the model.
  • Independent verification. Any third party — a committee, a funder, a journal — can verify a sealed record against the signing authority’s public key and the WorkSigned Record, without involving you or the data store.
  • Audit WorkSigned Record. The append-only, hash-chained WorkSigned Record plus per-credential and per-operation audit logs give a reviewable record of what was done, by whom, and when.
  • Key custody you control. In on-prem and sovereign modes the private signing key is institution-held. WorkSigned never holds a key it does not operate itself.
The platform is architected to answer the committee’s questions — integration, security, compliance, procurement — not only to impress the researcher. Deployment, the mount system, and the proof model are designed to be reviewable as a unit.
