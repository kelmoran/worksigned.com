Signing & Proof

How research records are signed and proven

WorkSigned uses a two-level cryptographic system: a daily seal signed by the operator, and a global anchor from an independent timestamping authority. Together they prove what was done, when, and that it has not been altered.

Overview

Every piece of research activity that WorkSigned captures is hashed the moment it is recorded. At the end of each day, all of those hashes are folded into a single value and signed. That signature, combined with an independent timestamp from a third-party authority, is the proof that the record existed at that time and has not been changed since.

The system has two levels. Level 1 is the researcher's own daily seal: a cryptographic signature over everything they did that day. Level 2 is the global anchor: a timestamp from an independent authority that proves the seal existed in the platform's log for that day. A researcher holds a small receipt (about 5 KB) that is sufficient for a third party to verify the entire day offline, with no access to WorkSigned's servers.

The methods

WorkSigned uses standard, publicly documented cryptographic primitives. There are no proprietary algorithms. Every step can be reproduced and verified by anyone with the public information.

SHA-256 hashing. Every tracked item (a file version, a database view, an email, a chat turn, a web search) is reduced to a 32-byte hash the moment it is captured. The hash is a fingerprint: any change to the content, even a single byte, produces a completely different hash. This is the same algorithm used by Bitcoin, TLS, and NIST-approved document systems.

RS256 digital signatures (RSA-2048). The operator of the WorkSigned software holds a private key and signs each day's seal. The public key is published. Anyone with the public key can verify that the signature is authentic. This is the same signature standard used by TLS certificates, code-signing certificates, and eIDAS-qualified electronic signatures.

Timestamping (RFC 3161). Once per day, the global root hash is sent to an independent Timestamping Authority (TSA). The TSA returns a signed token binding that hash to a time from the TSA's own clock. The TSA is a separate legal entity, often eIDAS-qualified, and is not controlled by WorkSigned or the researcher. This is the same standard used for legally binding electronic signatures in the EU.

Merkle trees. All of a day's hashes are arranged in a binary tree. The root of that tree is a single 32-byte value that represents the entire day's content. A Merkle tree allows a third party to prove that a specific item was in the signed set without needing to see or download the entire set. This is the same construction used in Bitcoin's lightweight (SPV) verification.

The daily seal

At the end of each day, WorkSigned collects every content hash captured that day: all file versions, all database views, all email records, all AI chat sessions, all web searches. These hashes are arranged in a Merkle tree. The root of that tree, along with a manifest (a table of contents listing what was captured), is combined into a single 32-byte value called the DAY FINAL.

The DAY FINAL is chained to the previous day's DAY FINAL. This makes the researcher's record a hash chain: day N's seal includes day N-1's seal. If any day is deleted or altered, the next day's signature will not verify, and the break is visible. This is the researcher's personal integrity guarantee, independent of the global log.

The operator then signs the DAY FINAL with their RSA-2048 private key. The signature binds the researcher's identity (via the user and project fields) to the day's content. The signed receipt, along with the manifest and the public key, is stored in the researcher's local database. This is the daily seal.

Each individual item in the day can also be proven independently. Because the day's hashes form a Merkle tree, any single file or record can be shown to be part of the signed day's root using only its own Merkle path (a few hundred bytes). A missing or corrupted local file does not invalidate the rest of the day: the other items still verify against the signed root, and the gap is visible and reportable.

The global anchor

Every day, all users' daily seals are collected into a single global Merkle tree. One timestamp from the TSA is taken over the root of that tree. This is the global anchor: the single time reference for the entire platform that day, regardless of how many researchers sealed.

The global log is chained across days. Today's global hash includes yesterday's global hash. If any day's log entry is deleted or altered, the next day's chain hash will not verify. The log is gap-detectable.

The researcher's receipt includes a Merkle path that proves their daily seal was in that day's global set. The path is about 640 bytes even for a platform with a million users. The researcher does not need to download or trust the full global log; the path is self-contained proof of membership.

Because there is only one TSA call per day for the entire platform, the cost is minimal (approximately $20/year) and does not scale with the number of users. A premium tier is available that adds a second, private TSA token over the researcher's own seal, giving their proof a self-contained time anchor with no dependency on the global log at all.

Verification

A third party (a court, an auditor, a grant agency) can verify any day of a researcher's record using only the small receipt that the researcher holds. No network access to WorkSigned is required. The steps are:

First, verify the operator's RS256 signature over the day's canonical string. This proves the operator attested to that day's content. Second, check the personal hash chain: today's DAY FINAL includes yesterday's DAY FINAL, so any gap or alteration is detected. Third, take the researcher's signature as a leaf and walk the Merkle path to the global root, proving the seal was in that day's global set. Fourth, for any specific file or record the verifier wants to check, prove it into the day's signed root via its own Merkle path. Fifth, verify the TSA token: its embedded hash must match the global chain hash, and the token's certificate chain must be valid. This proves the global set existed at the TSA's timestamp.

All of this works offline. The verifier needs the receipt (about 5 KB per day) and the file content they want to check. They do not need WorkSigned's servers, the operator's private key, or the full global log. Verification is deterministic: the same inputs always produce the same result, and the result is a binary pass/fail with no ambiguity.

Why this is court-recognized

Every component of WorkSigned's proof system is a standard, publicly documented method that is already accepted in legal proceedings. SHA-256 is an approved hash function by NIST (FIPS 180-4). RS256 is the signature algorithm in TLS 1.2 and 1.3. RFC 3161 timestamping is the standard for qualified electronic time stamps in the EU and is being adopted in US court proceedings for authenticating digital evidence. Merkle trees are a standard data structure in cryptography, patented in 1989 and used in Bitcoin's lightweight verification protocol.

There are no proprietary algorithms, no black-box trust, and no single point of failure that could invalidate the proof. The trust model is explicit: the researcher trusts the operator's signature key, the operator's integrity in running the software, and the TSA's clock. Each of these is a standard, auditable trust assumption. If any one is compromised, the others still hold. The research record itself, stored locally on the researcher's machine, is always accessible regardless of what happens to WorkSigned the company.
